# 纳川开源策略：对照 OpenClaw 的可执行方案

> 执行状态（2026-08-24）：Apache-2.0 公共核心已从严格 allowlist 生成全新历史候选，
> 社区治理与安全文件、中文安装维护入口、CI 和源码闭包收据均已纳入。官方安装包、
> 自动更新发布、代码签名、真实渠道长稳和企业云能力仍是独立门禁，不能由源码公开替代。

> 状态：研究与建议完成；未创建公开仓库、未上传代码、未发布安装包
> 日期：2026-08-24

## 1. 决策摘要

纳川应学习 OpenClaw 的“核心公开、扩展生态、透明安全边界、社区协作和可安装发行”，但不能照搬它的单操作者安全模型，也不建议把当前整个商业工作区原样公开。

建议采用：

- **Apache-2.0 的公共核心仓库**：本地优先桌面端、模型适配接口、协作运行时、个人知识库、企业授权接口及安全评测、扩展 SDK 和公开协议。
- **独立的商业云控制面**：托管租户运营、计费、反滥用、客户配置、SLA 运维、内部部署清单和商业管理后台不进入公共仓库。
- **商标与官方发行分离**：源码可自由使用，`纳川/Nachuan` 名称、官方签名安装包和官方云服务受商标与发行政策约束。
- **先治理和净化，再发布源码**：当前仓库不是可以直接推送到 GitHub 的公开源树。开源必须从明确 allowlist 生成干净候选仓库，并经历史密钥、许可证、恶意文件和客户数据审计。

这叫“开放核心 + 商业托管”，不是把闭源模块包装成开源。公开和商业边界必须写清楚。

## 2. OpenClaw 实际如何开源

截至 2026-08-24，OpenClaw 官方仓库体现了以下做法：

### 2.1 许可证和所有权

- 官方 `LICENSE` 是 MIT License，版权主体为 OpenClaw Foundation；`package.json` 也声明 `MIT`。
- `LICENSE` 末尾要求第三方改编代码的声明记录在 `THIRD_PARTY_NOTICES.md`。GitHub API 的自动许可证字段显示 `NOASSERTION/Other`，但仓库许可证正文和包元数据明确是 MIT；判断应以实际文件为准。
- 项目由非营利 OpenClaw Foundation 公开治理，维护者、贡献方式和安全报告路径公开。

### 2.2 公开范围

官方单仓库公开了核心 Gateway、CLI、控制 UI、桌面/移动应用、扩展、技能、配置、部署样例、测试、文档、更新信息和第三方声明。npm 包和安装脚本构成主要分发入口。

### 2.3 架构和生态

- Gateway 是本地控制面，连接模型、工具、消息渠道、UI、CLI 和伴随设备。
- 核心倾向保持精简；可选能力优先进入插件、技能或 ClawHub，而不是无限塞进核心。
- 插件 SDK 和契约是扩展边界；代码插件与 bundle 型技能/MCP 扩展分开。
- CONTRIBUTING 要求问题导向、验证证据、聚焦 PR、CI 和明确的 AI 辅助声明。

### 2.4 安全边界

OpenClaw 的官方 `SECURITY.md` 明确：它是本地优先、面向可信单操作者的基础设施，不把同一个 Gateway 当作敌对多用户之间的多租户安全边界。需要真实隔离时，应使用独立 agent、Gateway 或主机信任边界。

这点对纳川至关重要：OpenClaw 的开源方式值得借鉴，但纳川要服务企业多租户，就必须另建企业身份、RAG 权限、审计和租户隔离，不能引用 OpenClaw 的知名度来证明自身企业安全。

## 3. 为什么不建议“当前商用版全部原样开源”

全盘公开并不天然等于更安全、更好卖或更可信。当前直接公开会遇到：

- 工作区包含大量开发证据、临时目录、历史兼容代码和未完成产品边界，公开后用户无法区分正式能力与实验代码。
- 许可证和供应链虽已修复一批阻断项，但 FFmpeg、模型权重、全部第三方来源、恶意代码扫描和最终 SBOM 仍需上线前闭环。
- 正式包尚未 Authenticode 签名；自动更新的真实版本升级与失败回滚尚未在干净机验收。
- 企业 RAG 多租户权限尚处于架构设计阶段，现有知识库不能对外宣称企业级隔离。
- 仓库历史可能含已删除的凭证、真实账号、机器路径、客户数据或内部基础设施指针；只扫描当前 HEAD 不够。
- 计费、风控、生产拓扑、签名材料和客户运营数据公开会扩大攻击面，但对社区二次开发几乎没有价值。

正确做法是公开“可验证的产品核心与契约”，保留“托管运营秘密和客户数据”，而不是按目录数量追求开源比例。

## 4. 推荐公共范围

建议首个公共仓库包含：

```text
nachuan/
  apps/desktop/                 # 本地优先桌面客户端
  core/gateway/                 # 本地网关和请求契约
  core/orchestrator/            # 多模型协作、审批、任务状态机
  core/knowledge-personal/      # 个人知识库
  core/authz-contract/          # 企业授权接口、收据和 fail-closed 契约
  adapters/models/              # 不含密钥的模型适配器
  adapters/channels/            # 合法、可公开的渠道适配器
  sdk/plugins/                  # 扩展 SDK
  protocols/                    # 版本化 JSON Schema / OpenAPI
  evals/                        # 路由、协作、RAG 权限和安全评测
  docs/                         # 架构、安装、安全、隐私、贡献
  examples/                     # 全部为虚拟数据的样例
  THIRD_PARTY_NOTICES.*
  SECURITY.md
  CONTRIBUTING.md
  GOVERNANCE.md
  TRADEMARKS.md
  LICENSE
```

特别建议公开以下安全内容：

- 请求身份和授权接口、deny 优先、策略版本、审计收据等协议。
- 企业 RAG 权限执行点、模拟策略后端和跨租户对抗测试。
- 安装包内容闭包检查、许可证/SBOM 生成器、更新清单验证和安全回归。
- 渠道幂等、审批、恢复、模型锁定和真实结果收据的通用契约。

安全关键接口和评测公开有助于外部审计；商业价值可以留在托管控制面、企业运维和服务质量，不必靠隐藏核心安全逻辑维持。

## 5. 不进入公共仓库的内容

以下内容应永不提交或仅留在独立私有系统：

- 任何 API key、OAuth token、Cookie、真实手机号、真实渠道账号和签名私钥。
- 客户文档、对话、向量、反馈、训练样本、审计原文和个人信息。
- 代码签名证书、更新签名私钥、生产数据库凭证、KMS 材料和恢复密钥。
- 生产主机、网络、租户、告警、备份、部署库存和内部应急入口。
- 计费税务、反欺诈规则、滥用画像、人工运营后台和客户 SLA 数据。
- 未取得再分发权的模型权重、数据集、图标、字体、媒体二进制和第三方代码。
- 只用于内部安全研究、尚未修复的漏洞复现和真实攻击情报。

这些不是“闭源版偷偷保留核心能力”，而是凭证、客户数据、生产运营和受限资产的正常边界。

## 6. 许可证建议

### 6.1 公共核心：Apache License 2.0

建议纳川公共核心使用 Apache-2.0，而不是机械复制 OpenClaw 的 MIT：

- 同样允许个人和企业使用、修改、分发和商用，利于生态采用。
- 对公司型项目提供明确专利许可和专利诉讼终止条款，比 MIT 更适合长期企业协作。
- 允许纳川提供收费托管、企业支持、认证发行和商业扩展。

许可证必须由有权主体确认版权归属后再落地；如果现有代码包含雇员、外包、AI 生成和第三方改编内容，先做来源与权属清单。

### 6.2 贡献：DCO 优先

初期开源建议采用 Developer Certificate of Origin（DCO）和 `Signed-off-by`，不急于引入重型 CLA。若未来确需双重许可或基金会治理，再评估 CLA。所有 AI 辅助贡献要求贡献者确认理解代码、拥有提交权利并提供验证证据。

### 6.3 商标

Apache-2.0 不授予纳川商标权。单独发布 `TRADEMARKS.md`：

- Fork 可以说明“基于纳川”，不能冒充官方发行。
- 只有通过官方发布门、使用官方签名和更新源的构建可称“纳川官方版”。
- 社区版可自由改名和分发，不得使用容易混淆的图标、域名或公司背书。

## 7. 商业模式

公共核心不收费并不妨碍商业化。可收费的价值包括：

- 官方托管和企业 SLA；
- SSO/SCIM、组织管理、合规报告、专属区域、专属密钥和专属部署；
- 高可用控制面、策略同步、备份恢复、灾备和长稳监控；
- 官方签名安装包、受控更新通道、长期支持版本和安全响应；
- 企业连接器认证、迁移、实施、培训和技术支持；
- 评测服务、模型路由成本优化和商业流程定制。

原则是：用户能自行运行公共核心；企业付费购买省心、治理、合规、规模和承诺，而不是付费解除人为阉割。

## 8. 开源前发布门

### 8.1 源码净化

- 从 allowlist 生成新的公开候选树，不直接把当前工作区推送为 public。
- 扫描全部 Git 历史、LFS、发行附件、子模块和文档中的凭证、个人信息、客户数据和内网地址。
- 每个公开文件都有来源、版权和许可证；未知来源默认不公开。
- 第三方代码与二进制生成准确的 `THIRD_PARTY_NOTICES`、SBOM 和来源哈希。
- 不公开缓存、运行数据库、日志、真实配置、临时测试目录和本机证据。

### 8.2 产品真实性

- README 区分已实现、本地验收、远端干净机验收和生产就绪。
- 模型、渠道、企业 RAG、自动更新和安装包能力各有真实测试矩阵。
- 不以单元测试或进程存活替代真实渠道、真实升级、真实恢复和真实接收者验收。
- 企业权限未实现前，公开版明确标为单所有者知识库，不使用“企业级隔离”宣传。

### 8.3 安全治理

- `SECURITY.md` 提供私密漏洞报告路径、支持版本和响应规则。
- `CONTRIBUTING.md`、行为准则、治理规则、CODEOWNERS、Issue/PR 模板和版本策略齐全。
- CI 执行格式、类型、单元、集成、许可证、SBOM、秘密、恶意文件、依赖和构建闭包检查。
- Release 使用不可变 tag、可复现构建来源、构建证明和哈希；官方二进制在公开上架前完成代码签名。
- 自动更新只接受签名清单、固定 HTTPS 来源、版本防回退和失败回滚；源代码公开不能降低更新信任门。

## 9. 发行与生态建议

学习 OpenClaw 的优点，但按纳川产品形态调整：

- 公共源码和扩展 SDK 先行，官方插件目录晚于签名、来源验证和权限沙箱。
- 第三方插件默认不可信，声明权限、网络域、文件系统范围和模型数据去向；安装前由用户确认。
- 官方插件、社区插件、实验插件分级，不因进入市场就获得网关高权限。
- Windows 首选签名安装包、winget/可审计包管理入口和应用内签名更新；不把 `iwr | iex` 作为面向普通客户的唯一安装方式。
- 稳定、早期体验和开发三个更新通道使用不同签名/策略，不能共享可回退状态。
- 公共路线图以问题和验收证据为单位，不把内部未承诺计划包装成即将交付。

## 10. 分阶段执行

1. **OS-001 开源边界冻结**：确认公共模块、商业控制面、许可证、版权主体和商标策略。
2. **OS-002 公开候选树**：在项目主目录内生成隔离候选，不连接远端、不发布；完成全历史和第三方审计。
3. **OS-003 社区基础**：补齐 README、架构、安全、贡献、治理、行为准则、Issue/PR 模板和 DCO 检查。
4. **OS-004 可复现源码版**：源码检出后能在干净机测试、构建并生成相同内容闭包；先发布源码 alpha。
5. **OS-005 官方二进制**：代码签名、更新签名、真实升级/回滚、恶意软件多引擎证据和真实渠道长稳全部过门后，再发布官方安装包。
6. **OS-006 扩展生态**：插件清单签名、权限声明、隔离运行、撤下机制和安全响应成熟后开放目录。
7. **OS-007 商业云**：企业 RAG 权限、租户隔离、计费、审计和 SLA 完成独立验收后上线托管服务。

任何向 GitHub、Gitee、npm、winget、官网或更新源的写操作，都必须在发布候选审计完成后由用户单独确认。

## 11. 最终建议

纳川不应“等所有商业功能完成后一次性把整个工作目录全开”，也不应长期完全闭源。最佳路径是：

1. 先把本地核心、协议、安全门和评测整理成真正可独立运行的公共产品；
2. 用 Apache-2.0 建立可信、可商用、可二次开发的生态；
3. 把官方托管、企业治理、运营控制面和 SLA 做成商业价值；
4. 以签名发行、第三方来源、真实验收和透明安全边界建立品牌，而不是以隐藏代码建立壁垒。
