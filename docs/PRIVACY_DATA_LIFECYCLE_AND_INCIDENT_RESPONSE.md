# 纳川隐私、数据生命周期与安全事件响应工程基线

状态：工程基线，不构成法律认证或面向任一司法辖区的最终法律意见。上线前仍须由产品责任人、数据保护责任人和适用地区的法律顾问确认合同、告知文本、保存期限和通知时限。

机器可验收的数据资产清单与默认规则见 [`data-lifecycle.v1.json`](./data-lifecycle.v1.json)。本文解释执行机制；两者发生不一致时，发布必须停止并由责任人修订，不能静默选择其一。

## 1. 基线原则

1. 客户数据默认不用于训练、微调、蒸馏、评估集扩充或跨租户经验提取。任何例外必须取得独立、明确、可撤回的授权，并建立独立数据集、来源证明和删除链路。
2. 只收集完成已声明目的所必需的数据，保存期按部署、合同和法律义务配置，不把一个固定期限冒充全球通用期限。
3. 客户启用外部模型、渠道、同步或工具前，界面必须说明接收方、目的、发送的数据类别和适用保存策略；未启用即不外发。
4. 访问、导出、更正、删除、限制处理和可携带请求必须进入持久化工作流，不能靠人工聊天记录表示“已经处理”。
5. 删除不是单个 `DELETE` 语句，而是跨主库、派生索引、缓存、对象文件、渠道副本、处理者、备份和恢复流程的可重试事务。
6. 财务、争议、安全和法定义务数据若必须保留，只保留最低限度副本并限制无关处理；不能把“需要保留”解释为继续训练、推荐或营销。
7. 支持包、健康检查和事件证据默认只含封闭字段、聚合计数、时间和哈希，不复制客户正文、提示词、模型回答、令牌、密钥或本机路径。

## 2. 权利请求状态机

每个请求必须有稳定的 `request_id`、租户/数据主体范围、接收时间、身份核验结论、适用规则、冻结后的数据范围、逐存储执行回执以及最终结果。

允许状态只有：

`received -> identity_pending -> scoped -> executing -> partially_completed | completed | rejected_with_reason`

执行要求：

- 身份核验由部署所有者控制，并与请求风险相称；系统不得让未核验请求枚举其他人的数据。
- `scoped` 后生成版本化范围清单。范围改变必须生成新版本和原因，不能覆盖旧证据。
- 每个存储适配器返回幂等回执：存储 ID、动作、结果、影响数量或内容哈希、时间、错误类别和重试条件。
- 临时失败进入可重试状态；永久拒绝必须带适用理由和人工复核入口。
- 完成条件是所有必需回执齐全，而不是后台任务已经入队。
- 对已配置的外部处理者或接收方，记录通知、删除或限制处理结果；未知结果不得标记完成。
- 当前源码使用专用 `NCPR`、schema v1 SQLite 权利账本，只持久化主体和证据摘要；已版本数据库缺表、混入额外表/视图/触发器/显式索引或版本身份冲突时故障关闭，不能静默补表。初始化只认空库、完整且无数据的旧闭集或 NCPR/v1；部分旧表和带行未版本库必须显式迁移，并在拒绝前保持原 journal/schema/身份不变。即使并发进程在第二次 owner 检查前抢占，失败方也不得先切 WAL 或留下 schema/identity 变化。
- 新请求数量与主数据库页数有硬门禁；同一稳定请求的幂等重放在容量满时仍可读取原证据。非终态重试不能占用为真实终态回执保留的最后槽位。SQLite `max_page_count` 不限制被长读事务钉住的 live WAL，`wal_autocheckpoint`/`journal_size_limit` 也不是 live WAL 硬上限；生产部署仍须增加 WAL 水位/磁盘余量门禁、保留期执行器、受控归档和人工处置队列。

## 3. 导出合同

导出物采用版本化 JSON 清单和按内容寻址的附件，至少包含：范围版本、生成时间、来源存储、字段说明、附件哈希、缺失或受限项目及原因。密钥、访问令牌、内部签名材料、重放围栏和安装权威不得导出。

导出必须满足：

- 先核验身份和租户边界，再冻结读取快照。
- 大附件流式生成并限制磁盘、时间和内存；中断后不得留下可被其他用户读取的半成品。
- 导出下载采用短期、一次性或等价强度的授权；下载行为留最小审计证据。
- 生成失败不返回不完整文件作为成功结果。

## 4. 删除与凭据撤销事务

删除事务至少执行以下阶段，并允许在崩溃后按同一 `request_id` 恢复：

1. 冻结范围并写入不可变请求摘要。
2. 阻止范围内新的处理、同步、发送、索引重建和训练摄取。
3. 对外部模型、渠道、同步和工具目标发送删除或限制处理请求，并持久化结果。
4. 对凭据先在上游撤销或轮换；仅删除本地密文不能证明凭据失效。
5. 删除主内容、附件和对象文件；清除或重建派生摘要、嵌入、缓存、索引和媒体预览。
6. 对必须保留的财务或安全记录执行“保留并限制”，记录理由和复核日期。
7. 写入带范围和版本的删除墓碑，防止旧同步副本、缓存或备份复活数据。
8. 收齐逐存储回执后才进入 `completed`；任何未知结果保持 `partially_completed`。

备份恢复必须保持锁定，直到适用的删除墓碑、凭据撤销状态、重放下限和安装纪元重新应用并核验。旧备份不能重新激活已撤销凭据，也不能让已删除内容先对用户或智能体可见再异步清理。

## 5. 外部提供商和处理者

连接模型、微信/飞书、云同步、MCP、插件或商业结算服务时，产品必须保存版本化配置和用户可见说明，包括：

- 接收方和服务目的；
- 发送的数据类别及是否包含个人信息、客户内容或凭据；
- 传输触发条件、保存策略和可用的删除机制；
- 分包处理者或目的地变化的控制方式；
- 失败、超时或结果未知时是否可能已经产生费用或副作用。

用户关闭连接后，系统应立即停止新的外发；需要上游操作的撤销和删除进入持久化任务，不能只移除界面中的连接卡片。

## 6. 客户数据与模型改进

纳川的自我改进能力必须使用有来源证明、用途授权和版本冻结的数据。默认允许的数据只有：合成数据、明确授权的数据、许可兼容的公开数据，以及不含客户内容的运行质量指标。

禁止事项：

- 默认把会话、知识库、工作区、渠道消息、支持包或失败样本送入训练；
- 将跨租户内容混入共同评估集；
- 用“匿名化”标签替代可复现的去标识验证；
- 删除训练源后仍无机制定位受影响数据集、候选模型和评估结果。

候选数据集必须记录来源、许可/授权、去重、敏感信息检测、划分方法、污染检测和撤回映射。客户撤回授权后，相关样本进入删除事务，受影响候选不得继续晋级，除非重新训练或通过责任人批准的可验证处置。

## 7. 安全事件响应

事件响应按 NIST SP 800-61 Rev. 3 与 CSF 2.0 的准备、检测、响应、恢复和改进闭环组织。事件计时从首次获得有支持证据的知悉时刻开始，不以工单创建时间延后。

最低流程：

1. 分级并保存最小、脱敏、内容哈希化的时间线证据。
2. 先控制仍可被利用的入口；泄露或疑似泄露的凭据优先在上游撤销/轮换。
3. 确认受影响租户、数据类别、处理者、时间范围、完整性和可用性影响。
4. 根据司法辖区、控制者/处理者角色、风险和合同，由法律责任人决定监管机构、客户、数据主体和合作方通知。
5. 记录决定、通知回执、缓解措施、恢复验收和复盘改进；不能因无需外部通知而删除内部事件记录。
6. 恢复前验证删除墓碑、安装纪元、凭据状态、队列幂等性和重放围栏，防止恢复过程制造第二次事件。

通知时限不能在代码里假定为全球统一。适用 GDPR 且纳川作为控制者时，监管机构通知通常以可行情况下知悉后 72 小时为关键上限；作为处理者时，应无不当延迟地通知控制者。实际义务必须由角色、风险和适用法判断。

## 8. 发布验收门

PR-011 只有同时满足以下证据才可从“工程基线”升级为生产关闭：

- 数据资产清单覆盖真实持久化位置，并由测试阻止新增存储绕过登记。
- 权利请求、导出、删除和限制处理状态机有崩溃恢复、重试、并发和越权测试。
- 每类存储具有真实适配器和逐存储回执；未知结果不会被归类为成功。
- 备份恢复在删除墓碑和安装纪元重锚完成前不可服务。
- 凭据删除测试包含上游撤销/轮换证据，且旧凭据验证失效时不打印秘密。
- 外部处理者配置与用户界面披露一致，并能停止新外发。
- 支持包和事件证据通过恶意秘密、客户正文、本机路径和异常日志注入测试。
- 法律/合同责任人确认目标地区的告知、期限、处理者合同、跨境和通知规则。
